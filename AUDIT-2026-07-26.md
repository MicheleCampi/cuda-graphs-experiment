# Pre-publication audit — CUDA graphs trade-off article

Date: 2026-07-26. Scope: draft `article-cuda-graphs-tradeoff.md` audited against
raw server logs and result JSON in this repo, before repo go-live and article publication.
Method: open the raw vLLM server logs, not only the report JSON.

Engine under test: vLLM **0.23.0** (recorded at runtime in all 64 result files).
Note: the 0.21 source worktree does NOT describe this experiment.

## Verified correct (no change needed)

- Throughput chain: wall-clock 202.0s vs 191.6s reproduces -5.15% at fixed 64,000 output tokens.
- TPOT table: all four ON/OFF deltas recompute from the reported values.
- Energy guard-rails pass (`aggregate_energy.py` -> "TUTTI OK"); `energy_source: counter` in 12/12 runs.
- No preemption events in server logs.
- Graph capture happens during engine init and completes before the server accepts traffic:
  `gpu_model_runner.py:6585` -> 3s / 0.58 GiB (7B), 9-10s / 1.01 GiB (32B). No runtime capture cost.
- 32B mean board power ON > OFF (203.0W vs 199.3W) is NOT an artefact of active-window
  dilution: within the ON arm, active fraction rises 0.738 -> 0.763 while power *falls*
  203.5 -> 202.4W. Opposite sign to the dilution hypothesis, which is therefore rejected.

## Findings

### F1 (severe) — serverless break-even uses the wrong load regime
The ~2,550-request break-even derives from *sustained* throughput (concurrency 64, ~2.9 ms/req).
The serverless bullet applies it to a scale-to-zero replica, which runs at concurrency 1.
In the sporadic regime the relevant saving is per-request latency:
TPOT 9.11 vs 9.93 ms x 128 tokens = ~105 ms/request -> break-even ~70 requests.
The stated conclusion ("may never break even") is inverted by this repo's own data.
Regenerate: TPOT values in `deep_analysis.py` output, sporadic cells.

### F2 (severe) — "active fraction barely moves" / "idle tail symmetric" are false (32B)
Measured: active 0.725 (OFF) vs 0.754 (ON); non-generating tail 110.1s vs 98.4s in a fixed 400s window.
Regenerate: `python3 aggregate_energy.py` (active column).

### F3 (severe) — the 7B "+0.3% is a floor" argument rests on an unsupported assumption
The 60s window contains a ~15s head (bench dataset load/tokenisation; token counters are flat
until then) plus a tail: up to 40% of the window generates no tokens (ON rep1: span 36s of 60s).
Solving the two-power system per model gives P_active ~= 234W and P_non-generating ~= 224W on the 7B
(vs 233W / 108W on the 32B), i.e. the non-generating time is not idle in any usable sense.
Two equations, four unknowns: not separable from the stored aggregates, so no mechanism is asserted.
Consequence: report energy over the active span, or declare the head/tail structure explicitly.
Regenerate: token onset/offset from `phase_timeline.samples` in `results-energy-tight/*.json`.

### F4 (medium) — cold-start delta is capture PLUS compilation, not capture alone
Warm-cache matrix runs in `results/`:
| model | init ON | init OFF | delta | capture | torch.compile | attributed |
|---|---|---|---|---|---|---|
| 7B  |  8.15s (n=9)  | ~2.0s | 6.15s | 3.0s (49%) | ~2.9s (47%) | 96% |
| 32B | 18.57s (n=10) | 3.62s (n=10) | 14.95s | 9.1s (61%) | 5.21s (35%) | 96% |
`--enforce-eager` disables the compiled path as well as capture. The published +7.4s / +15.9s
are consistent with these deltas but must not be attributed to capture alone.

### F5 (medium) — inherited claim from the eBPF post
"a large slice of that warmup is CUDA graph capture" holds for the 32B (61%), not the 7B (49%,
with compilation nearly equal). Restate or retract; the earlier post needs the same correction.

### F6 (medium) — "all eight cells"
The matrix has 8 configurations but 4 ON-vs-OFF comparisons. The claim as written is not
supported by a four-row table.

### F7 (medium) — cold-start table: undeclared cell selection and one contaminated rep
Published figures take the *sustained* cell only, criterion undeclared; the *sporadic* cell
would give +9.6s for the 7B. Cause: `cold_start_s` is measured per rep, so rep1 of each campaign
carries the cold AOT compile (7B sporadic ON r1 = 51.76s vs ~36.6s for reps 2-5; 32B first start
compiles in 27.00s and *saves* the AOT cache, later starts *load* it at 5.2s).
Corrected, pooling both profiles and dropping the contaminated rep:
7B 37.04s (n=9) vs 30.00s (n=10) = **+7.04s**; 32B 56.03s vs 40.14s (n=10) = **+15.89s**.
Regenerate: per-rep `cold_start_s` across `results/*.json`; `aot=save|load` from server logs.

### F8 (minor) — reported standard deviations are polling granularity
`wait_until_ready` sleeps 2s only on the failure branch, so readiness is detected on a ~2s grid;
observed values are quantised in ~2.02s steps. The +-1.50 / +-1.00 figures are instrument
granularity, not physical variance, and "37.0 s" overstates precision. The deltas (7s, 16s)
are 3-8x the step and remain resolvable. A systematic ~+1s overstatement affects the absolute
level in both arms and cancels in the delta.

### F9 (minor) — power envelope
Draft states a 350W envelope; measured `power_max_milliwatts` = 380.8W (32B ON rep2). Verify the card spec.

## Observations (no action)

- First 7B start in `results/vllm_server.log` runs at `max_seq_len=32768`; `MAX_MODEL_LEN` is a single

- One 7B init outlier in `results-energy-tight`: 84.70s vs 8.68-8.85s for five identical starts,

## Hypotheses raised and rejected during the audit

- **Window-dilution explanation of the 32B power delta.** Proposed: ON draws more mean power
  only because its longer active span dilutes less idle time inside a fixed window. Rejected on
  within-arm evidence (active 0.738 -> 0.763 with power falling 203.5 -> 202.4W): the dilution
  hypothesis predicts the opposite sign. The draft's power claim survives.
- **Prefill as the source of the window head.** Proposed: the first ~15s of each window is
  prefill, hence not idle. Rejected: `prompt_tokens` and `generation_tokens` start advancing at
  the same timestamp, so nothing is running on the GPU before that point. The head is bench-side
  dataset load and tokenisation.
- **F5 itself: an inherited error in the eBPF post.** F5 recorded that the earlier cold-start post
  attributed "a large slice" of warmup to CUDA graph capture, and that the attribution was wrong on
  the 7B. Checking the published post before writing the correction showed it says no such thing: it
  ran with `enforce_eager=True` precisely to keep the trace readable, so graphs were disabled and
  unmeasurable there, and it names graph capture only prospectively, as one plausible lever on warmup.
  The faulty sentence was in this article's own summary of that post. No erratum is owed on the
  earlier post; the passage here was rewritten to describe it accurately.

- **vLLM 0.21 as the reference source.** The `/root/vllm-021` worktree does not describe this
  experiment; all 64 result files record 0.23.0. Verification was done against this repo's own
  server logs instead.
